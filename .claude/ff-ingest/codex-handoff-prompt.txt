CONCURRENCY — avoid colliding with the Claude cron backstop
============================================================
There is a macOS user crontab entry (`ff-ingest-resume`, fires every 15 min)
that invokes `claude -p` headlessly to keep working this same plan whenever
a live Claude session isn't running. Once Adnan's weekly limit is hit, those
invocations will simply fail/no-op (harmless), and will resume working
automatically once the limit resets. To avoid it colliding with YOU (e.g.
both grabbing the same next-batch simultaneously and double-rasterizing):

Hold the same lock file the cron already respects, for as long as you are
actively working:
  nohup sleep 999999 >/dev/null 2>&1 &
  echo $! > /tmp/ff-ingest.lock
When you stop working (session end, or handing back to Adnan/Claude), release it:
  kill $(cat /tmp/ff-ingest.lock) 2>/dev/null; rm -f /tmp/ff-ingest.lock
This is the exact same PID-liveness lock resume.sh checks — holding it
makes the cron skip its tick with "still running — skip this tick" instead
of firing a colliding duplicate run.

PER-BATCH WORKFLOW (6 docs at a time — hard rate-limit lesson, don't do more)
============================================================
1. Compute next batch:
     zsh ".claude/ff-ingest/whats_next.sh"
   Prints the next 6 un-ingested FF ids.

2. Prep (rasterizes pages to JPGs + builds the extraction prompt per job):
     zsh ".claude/ff-ingest/ff_prep.sh" /tmp/ff_batchNN.tsv FF0aa FF0bb FF0cc FF0dd FF0ee FF0ff
   This produces 12 request dirs (one per doc × 2 jobs: metadata.a, summary)
   and prints a manifest (also written to /tmp/ff_batchNN.tsv):
     ff_id \t job \t request_dir

3. For EACH of the 12 request dirs, you (or your own parallel
   sub-agents/tool-calls, if Codex supports spawning them — otherwise do it
   yourself sequentially) must:
     a. Read <request_dir>/system.txt and <request_dir>/user.txt — user.txt
        contains the exact JSON schema to fill in (a metadata OR summary
        schema depending on job).
     b. Read <request_dir>/page-001.jpg through page-0NN.jpg (however many
        are present, up to 20) — these are the actual scanned magazine
        pages. Actually look at them.
     c. Extract per the schema. Follow the schema's own rules exactly
        (author/authority-resolution rules, work_type enum, etc. — they're
        spelled out in system.txt/user.txt, don't improvise around them).
     d. Write the resulting single JSON object to
        <request_dir>/response.json (that exact filename).
   This step is naturally parallelizable (12 independent, order doesn't
   matter) — if your tool can fan out sub-tasks, do all 12 concurrently;
   if not, a sequential loop is fine, just slower.

4. Once all 12 response.json files exist, finalize the batch:
     zsh ".claude/ff-ingest/ff_finalize.sh" /tmp/ff_batchNN.tsv "batch NN (FF0aa-FF0ff)"
   This collects the JSON, emits/writes the Astro markdown files under
   apps/site/src/content/primary-works/ff*.md, force-normalizes
   publisher_id/issuer_id to "freedom-first" on every ff*.md (needed for
   periodical series grouping), runs `astro sync`, commits, does
   `git pull --rebase origin main && git push origin main`, and purges
   /tmp/llm-extract-requests/* (only AFTER finalize — never purge mid-batch
   or you'll delete another batch's in-progress rasterization).
